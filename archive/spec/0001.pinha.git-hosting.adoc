== Context

Pinha hosts both ordinary Git repositories and native Jujutsu repositories. They share lifecycle, access, browsing, Git interoperability, and operations, but keep their own source-of-truth model: Git refs remain authoritative for a Git repository, while a Jujutsu repository owns a public Jujutsu view and exposes Git refs as a compatibility projection. link:0004.pinha.jj-hosting.adoc[Native Jujutsu hosting] defines the native view and synchronization protocol.

== Scope

* Create, discover, delete, and browse repositories of persisted kind `git` or `jj`, preserving Git branches and default-branch workflows for plain Git while supporting branchless changes, bookmarks, and visible heads for Jujutsu.
* Serve Git-compatible clone, fetch, and push over smart HTTP and SSH for both kinds, with authenticated global read access, owner-or-admin writes, one filesystem root, coherent backup, structured logs, OpenTelemetry traces, and no quota.

== Abstractions

=== Repository

A named directory with a persisted kind and owner. A `git` repository is a standard bare Git repository: its refs are authoritative and a live symbolic `HEAD` names its default branch. A `jj` repository is a server-managed Jujutsu repository using the production Git commit backend: its published view from link:0004.pinha.jj-hosting.adoc[Native Jujutsu hosting] is authoritative and it has no server workspace, current revision, required bookmark, or universal head.

The owner is the user named by the opaque `uid` minted by link:0002.pinha.account.adoc[Account]. Every authenticated user reads every repository; only its owner and admins write. Kind controls repository semantics and storage, not authorization or which users may use Git transport.

=== Revision

A commit selected by a branch or bookmark, tag, full or unique commit-ID prefix, or full or unique Jujutsu change-ID prefix. Resolution for a Git repository uses its reachable refs. Resolution for a Jujutsu repository uses its published view. An ambiguous namespace or prefix, a conflicted bookmark or tag, or a divergent change returns every candidate instead of choosing one. Workspace symbols and arbitrary server-side revsets are not accepted.

=== Commit

An immutable commit with metadata, parents, tree, and commit ID. A Git commit may also carry Jujutsu headers or a legacy change-ID trailer; Pinha preserves and renders valid metadata without changing the repository kind. In a Jujutsu repository, commits additionally participate in stable change identity, predecessor relationships, divergent rewrites, and conflict representation defined by its pinned repository format.

=== Git projection

The subset of a Jujutsu repository's published view that Git can express. A resolved bookmark is exported as `refs/heads/<name>` and a resolved tag as `refs/tags/<name>`. Anonymous visible heads and conflicted reference targets remain native-only unless another exported ref reaches their commits. Internal Jujutsu retention refs are hidden and unwritable.

Git repositories have no projection: their branches, tags, and `HEAD` are source data. A Git push mutates those refs directly; a Git-compatible push to a Jujutsu repository is imported into the server view as described below.

=== Repository presentation

The UI vocabulary and emphasis appropriate to the repository's history. A plain Git repository is labeled `Git`, displays branches and a default branch, and treats commit IDs as primary. A native repository is labeled `Jujutsu` with visible Git compatibility, displays bookmarks and visible heads, emphasizes change IDs, and renders commit IDs and bookmarks as supporting coordinates.

A Git-kind repository whose reachable commits contain valid Jujutsu change identity is labeled `Jujutsu via Git`. It receives change/bookmark presentation because that matches the producing workflow, but remains a Git repository: the hint never creates native state, changes authorization, or claims native synchronization. The presentation is derived on read and is not persisted.

=== Surface

The web surface comprises the repository UI and raw-file routes, Git smart HTTP, native Jujutsu routes for `jj` repositories, and account routes. The SSH surface accepts one restricted Git or native-Jujutsu exec channel per connection. The operating surface is the repository root, listeners and public URLs, a pinned Jujutsu adapter for native repositories, JSON widelogs, OpenTelemetry traces, and supervised maintenance. Credentials are defined by link:0003.pinha.account.authentication.adoc[Account authentication].

== Mechanics

=== Repositories

The operator sets one repository root, such as `/srv/pinha`, with no nesting (`$ROOT/foo.git`, never `$ROOT/group/foo.git`). A single OS user owns the root and every directory beneath it; application authorization, not Unix ownership, decides who may mutate a repository.

==== Create

`POST /repos` accepts a `name` and `kind` from any authenticated user, who becomes the owner. An omitted kind means `git`, preserving the existing API and plain Git workflow. Pinha builds the complete repository in a temporary sibling directory, writes `pinha.kind` and `pinha.owner`, then atomically renames it to `<name>.git`. Concurrent creates of one name serialize and the loser receives `409`.

For `git`, Pinha initializes an ordinary bare repository with HTTP receive enabled. `HEAD` may initially name an unborn branch, but Pinha creates no commit. For `jj`, Pinha initializes the Git commit backend and native operation/view state; its published view contains only Jujutsu's root commit and no bookmark or tag. The kind marker becomes visible only after the corresponding storage is complete.

==== Discover and convert

The listing considers each direct child ending in `.git`. A valid bare repository with no `pinha.kind` marker remains `git`, which makes repositories created by hand and installations predating this field backward compatible. It is never silently converted because Jujutsu state cannot be reconstructed from refs alone.

An owner or admin may explicitly convert a Git repository to Jujutsu under its write lock. Conversion initializes a published view from the branches, tags, reachable commits, and valid Jujutsu headers that exist at that moment, then writes the `jj` marker atomically. It cannot recover anonymous heads, predecessor maps, conflicts, or operations absent from Git. A Jujutsu repository does not convert back by changing its marker; its Git projection already supplies plain Git access without discarding native state.

A directory with invalid Git data, an unknown marker, or incomplete native state is reported as unavailable and is never silently repaired or reinitialized. Non-repository directories are skipped.

==== Delete

`DELETE /r/:repo` is allowed to the owner and admins. Pinha takes the repository write lock, renames `<name>.git` out of the listing so new requests stop resolving it while in-flight readers drain, then removes the renamed directory asynchronously. Rename is delete plus create; history is updated through the transport appropriate to its kind.

=== Access

Every authenticated user may list, browse, fetch, and read raw files from every repository using a session, token, or SSH key. Git `receive-pack`, native publication, kind conversion, and deletion require the owner or an admin. Refusal is `403` over HTTP or a message on stderr with a non-zero SSH exit; no repository writer starts.

Ownership lives in the bare Git `config` as `pinha.owner`, holding a user's stable `uid`, so a coherent filesystem restore carries its owner and username, email, or credential changes do not transfer ownership. Rendering an owner is one lookup by `uid`, batched for listings. An owner may be assigned with `Pinha.Repos.set_owner/2` from the release console or repository page; both accept a username and persist the corresponding `uid`, which the page also displays.

A repository with no owner, or with a `uid` that no longer exists, remains readable and is writable only by admins until one assigns an owner. The same authorization function gates HTTP, SSH, Git receive, native publication, conversion, and deletion.

=== Browsing

The repository list and summary display a visible kind badge. `Git` means refs and `HEAD` are authoritative. `Jujutsu` means the native view is authoritative and Git remains compatible. `Jujutsu via Git` identifies valid Jujutsu change metadata inside a Git-kind repository without claiming native sync.

Git pages call `refs/heads/*` branches, show a live `HEAD` target as `default`, and title history `Recent commits`. Jujutsu presentations call them bookmarks, show `HEAD` only as a muted `git HEAD` compatibility hint, title history `Recent changes`, and give change IDs more emphasis than bookmark or commit IDs. Text carries the distinction; color is supplemental.

Routes are:

* `GET /` — repository list.
* `GET /r/:repo` — summary, references, and history.
* `GET /r/:repo/tree/:rev/*path` — file listing or blob at an explicit revision.
* `GET /r/:repo/change/:id` — visible and retained evolution of a Jujutsu change ID.
* `GET /r/:repo/commit/:id` — one exact commit's metadata, parents, conflicts when present, and full diff.
* `GET /r/:repo/raw/:rev/*path` — raw bytes when the revision resolves to one ordinary blob.

For Git, a live default branch may be the first browse suggestion; without one, the summary shows the available branches and tags. For Jujutsu, revisionless browsing stops at the summary: one visible head may be offered first, several are all offered, and a date never elects one. Names containing `/` are carried intact in generated links, and ambiguous revisions lead to a chooser.

Git reads use the bare repository directly. Native reads pin one stable server view and use the Jujutsu adapter's change, tree, predecessor, and conflict semantics. A `Jujutsu via Git` page may display change IDs preserved in commits, but does not infer the missing public view or exact operation history.

=== Native synchronization

Only repositories of kind `jj` expose the clone, fetch, publication, concurrency, and evolution behavior in link:0004.pinha.jj-hosting.adoc[Native Jujutsu hosting]. A Git repository remains fully usable through Git and `jj git`; valid Jujutsu commit headers alone do not enable the native endpoint or change its persisted kind.

=== Git clone and push

Smart HTTP uses `GET /r/:repo/info/refs`, `POST /r/:repo/git-upload-pack`, and `POST /r/:repo/git-receive-pack`. SSH clone URLs use `git@<host>:<name>.git` and execute `git-upload-pack '<path>'` or `git-receive-pack '<path>'`. Git and `jj git` clients use these endpoints for both repository kinds.

For Git repositories, `upload-pack` advertises branches, tags, and live `HEAD` normally. `receive-pack` accepts create, update, delete, and force-push for `refs/heads/*` and `refs/tags/*`, with no protection rules or extra namespaces; Git's ref locks resolve concurrent updates. The received refs and objects are authoritative, commits are never rewritten, and ordinary Git administration and backup remain valid.

For Jujutsu repositories, `upload-pack` advertises only the Git projection and a live projected `HEAD` hint. Pinha hides `refs/jj/*` and private namespaces, does not synthesize a default branch, and refuses fetching an unadvertised anonymous head by object ID. `receive-pack` rejects internal namespaces and conflicted projected targets, serializes with native writers, imports the ref delta as one server operation, refreshes the projection, and acknowledges only after that operation is durable. Interrupted integration is recovered from its mutation journal before another writer runs.

`jj git clone`, `jj git fetch`, and `jj git push` remain ordinary Git workflows. They preserve opaque Jujutsu commit headers that Git transports but cannot synchronize anonymous heads, a conflicted ref target, an exact predecessor map, or either side's operation log. Full branchless collaboration uses the native protocol against a `jj` repository.

After a successful receive, supervised maintenance may update the native index and runs Git repacking appropriate to the repository kind. A Jujutsu repository protects objects retained by current or retained operations through hidden refs; Git pruning never decides native history retention by itself.

==== SSH

The release runs Erlang's `:ssh` daemon under its supervisor on a configured port, defaulting to `2222`, with no OpenSSH daemon, OS account per user, or `authorized_keys` file. Only public-key authentication is offered. Every client connects as the single username `git`; a SHA-256 key fingerprint resolves the application user once and binds the connection to that user.

A Git session may execute exactly one `git-upload-pack` or `git-receive-pack` against one repository. The command is parsed without a shell into an allowlisted verb and a path validated by the same `<name>.git` rules as HTTP. A leading `/`, `~/`, or `r/` is normalized. Shells, PTYs, sftp, forwarding, `git-upload-archive`, arbitrary environment variables, and a second exec are refused. `GIT_PROTOCOL` alone may pass when its value matches `version=2`.

Git is spawned from an argv list. Client input and output stream under SSH window flow control rather than buffering a pack in BEAM memory. Protocol-v2 flush and half-close behavior is translated explicitly, and the channel returns Git's exit status. A successful receive enters the same authorization, logging, tracing, and maintenance path as HTTP.

The Ed25519 host key is generated once with mode `0600` in a configured directory defaulting to `$ROOT/.pinha/ssh`. It survives restarts and deployments, and its fingerprint is logged at startup. Repository pages render the configured SSH host and port beside HTTP and native clone URLs. The native exec verb from link:0004.pinha.jj-hosting.adoc[Native Jujutsu hosting] receives the same restrictions and is rejected for a Git repository.

=== Operating

Deployment is one Pinha release plus the repository root. Configuration provides the root path, HTTP listen address, public base URL, SSH port and host-key directory, advertised SSH host, the pinned Jujutsu adapter version, and optional OTLP endpoint and credentials. Adapter compatibility is checked only for Jujutsu repositories. A native format upgrade snapshots the complete directory and runs under its write lock before exposing the new view; it never rewrites a Git-kind repository.

Logs go to stdout as JSON with one canonical widelog per HTTP request or SSH session. It records timestamp, event, repository kind and presentation, transport (`web`, `git-http`, `git-ssh`, `jj-http`, or `jj-ssh`), route or exec verb, revision when applicable, status, duration, byte counts, authenticated user, and user agent or peer. A native mutation also records its operation/view token and a bounded summary of changed heads and references. Subprocess or adapter errors are captured into that event rather than interleaved as unstructured output.

OpenTelemetry spans cover HTTP, database access, Git advertisements and subprocesses, native fetch/publication, repository integration, maintenance, and SSH sessions as applicable. Without exporter credentials the spans are created and dropped locally. Interrupted transports still finish their span and widelog with transferred bytes and failure reason.

Backup and restore copy or snapshot each complete `<name>.git` directory. A Git repository remains a conventional bare-repository backup. A Jujutsu backup includes its Git backend and native sidecar as one consistency unit; a live file-by-file copy takes the repository read lock, while a volume snapshot may provide that boundary. There is no export format and no quota: a full disk fails a mutation without advancing authoritative state.

== Data Model

Every repository is rooted at `$ROOT/<name>.git` and contains a valid bare Git layout with `HEAD`, `config`, `objects/`, `refs/heads/`, `refs/tags/`, and optional `description`. Its `config` contains `http.receivepack true`, `pinha.kind` (`git` or `jj`), and, when assigned, `pinha.owner` with the owner's `uid`. An absent kind means `git`; an unknown value is invalid.

For kind `git`, the bare layout is complete authoritative storage. `HEAD`, branches, tags, objects, and reflogs retain their normal Git meaning, and `.pinha/jj/` is absent.

For kind `jj`, the same directory also contains `.pinha/jj/` with the operation store, operation heads, views, indexes, commit-backend metadata not encoded by ordinary Git objects, and mutation-recovery journal. The Git object database is the production commit backend; `refs/heads/*` and `refs/tags/*` are derived projection state; hidden `refs/jj/*` retain otherwise anonymous or historical objects. The latest complete server operation and view are authoritative.

The derived repository presentation is not stored. Pinha determines it from `pinha.kind` plus valid Jujutsu identity in the reachable history, so `Jujutsu via Git` never changes the underlying model. Backups, moves, and restores treat the whole directory as one unit for either kind.
