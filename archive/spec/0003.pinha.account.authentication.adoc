= Account authentication

:status: Draft

== Context

We need auth. The web UI authenticates with passkeys; git clients cannot, so they authenticate with an access token over HTTP or an SSH key, both registered in the UI.

== Scope

* Users with passkey sign-up and sign-in, managing passkeys, invites, access tokens, and SSH keys from the UI, plus claiming the server and recovery.
* Authenticated git transport: clone, fetch, and push carry an access token over HTTP Basic, or an SSH key over the SSH listener.

== Abstractions

=== User

See link:0002.pinha.account.adoc[Account]. Authentication operates on that user: passkeys are bound to its WebAuthn `handle`, sessions prove a sign-in for it, and tokens and SSH keys are scoped to it.

=== Session

A browser's proof of a completed sign-in. The cookie carries 32 random bytes; the server stores only their SHA-256, so a dump of the table cannot be replayed as a login.

=== Access token

What git sends. Minted in the UI, shown once, stored as a SHA-256 hash, and presented as the HTTP Basic password on every smart-HTTP request. Tokens carry a label, an optional expiry, and the time they were last used.

=== SSH key

What git presents over SSH. A public key pasted into the UI in `authorized_keys` form and stored whole next to its SHA-256 fingerprint, which is unique across all users so one key cannot belong to two people. A key carries a label and the time it was last used; it has no expiry, and deleting the row revokes it.

=== Invite

What admits a registration. Minted by an admin, shown once, stored as a SHA-256 hash, and pasted into the sign-up form by the person registering. An invite carries a label and an expiry, and admits exactly one registration.

=== Repository

See link:0001.pinha.git-hosting.adoc[Git hosting].

=== Surface

The routes in link:0001.pinha.git-hosting.adoc[Git hosting], plus sign-up, sign-in, sign-out, and settings. Every route other than the sign-in surface requires an authenticated user. Reading a repository asks for nothing more; writing or deleting one asks for its owner or an admin, by the rule in link:0001.pinha.git-hosting.adoc[Git hosting]. The SSH listener admits only registered keys, and the user it resolves is subject to the same rule.

== Mechanics

=== Sign up

`GET /signup` collects a username, an email, and a passkey label. The server validates the username per link:0002.pinha.account.adoc[Account] (required, unique, at most 64 characters, not blank) and the email, then generates a challenge, stores it in the session, and returns it with the relying party ID taken from the host of the configured public base URL. The browser calls `navigator.credentials.create`, and the server verifies the attestation with `wax_`, stores the credential, and starts a session. A user may register a passkey per device, and settings registers further ones the same way. WebAuthn requires a secure context, so production must be served over HTTPS; `localhost` is exempt, which is what makes development work.

A registration is admitted by a token and nothing else. The first one takes the claim token below; every later one takes an invite pasted into the form next to the username, email, and label. The token is checked when the challenge is requested and spent in the transaction that stores the credential, so a challenge sitting in a browser cannot outlive its window and two people holding one invite cannot both register. Blank or duplicate usernames are rejected with a useful error before a challenge is issued, and the username is stored as supplied.

=== Claiming the server

A fresh server belongs to nobody until the operator proves they are the operator. A node that starts with no users mints a claim token, 32 random bytes kept in memory, and writes the claim URL once on stdout as `/signup?claim=<token>`. The operator reads it from the logs of the deployment they just started, or mints another from the release console with `Pinha.Accounts.Registration.claim()`. The token lives fifteen minutes and dies with the node, so there is nothing persistent to steal and a token that expires before the operator gets to it is replaced by asking for another.

The browser carries the token to the challenge request, which compares it against the one in memory in constant time and records that it did in the session, next to the challenge. Storing the credential spends the token, so a second holder of the same token is refused at the moment it matters. A running node mints nothing further on its own once a user exists: deleting the last user leaves a server that admits no registration until the operator asks for a token.

=== Invites

An admin mints an invite at `/settings`, rendered once as `pinha_invite_<32 bytes>` and stored as a hash. Handing it over is the admin's problem, by whatever channel they already have with the person, because the server delivers no mail. An invite expires seven days after it is minted and admits one registration. Settings lists what is outstanding, who minted it, and whether it was used — showing the consuming account's username in `Used by`, never its email — and deleting the row revokes it.

Sign-up looks the invite up by hash, which is the same single indexed read as an access token, refuses one that is expired or already spent, and records it in the session with the challenge. The registration inserts the user, stores the credential, and marks the invite consumed in one transaction, so a ceremony that fails leaves the invite usable and one that succeeds cannot be replayed.

=== Sign in

`GET /signin` issues a challenge with no credential list, so the browser offers any discoverable passkey for the relying party and the user is identified by the handle the authenticator returns. `wax_` verifies the assertion, and the stored signature counter must advance: a counter that fails to move is how a cloned authenticator announces itself, and the attempt is refused and logged.

=== Sessions

A successful ceremony mints 32 random bytes, stores the SHA-256, and writes the raw value into the signed session cookie after renewing the session, so a fixated session cannot survive the sign-in. Sign-out deletes the row. Sessions expire 60 days after they were last used. The session logic follows the `phx.gen.auth` plug of the same shape.

=== Git transport

`GET /:repo/info/refs`, `POST /:repo/git-upload-pack`, and `POST /:repo/git-receive-pack` accept HTTP Basic credentials: the user's email as the HTTP username and an access token as the password (the public username is not used for git transport). The token is looked up by SHA-256 hash, which is a single indexed read, and an expired token is refused. `last_used_at` is written at most once an hour per token, so a clone does not turn into a write per request. A request with no credentials gets `401` with a `WWW-Authenticate: Basic` challenge, which is what makes git prompt and what lets credential helpers store the token. SSH carries no Basic credentials: the connection is already authenticated by key before any git command runs, which is why `git@<host>:<name>.git` pushes without a prompt. Either transport, once it knows the user, checks the repository's owner before starting git; authentication says who is asking, and link:0001.pinha.git-hosting.adoc[Git hosting] says what they may do.

=== SSH keys

`/settings` takes a key pasted in `authorized_keys` form: type, base64 body, and an optional comment on one line. The server parses it with `:public_key`, accepts Ed25519, ECDSA, and RSA of at least 2048 bits, refuses DSA, and stores the key with its SHA-256 fingerprint, falling back to the comment when the label field is left blank. A fingerprint already registered is refused whoever pastes it, so a second account cannot quietly attach itself to someone's key. Settings lists each key by label, algorithm, `SHA256:` fingerprint, and last use, and deleting the row revokes it.

Authentication looks the offered key up by fingerprint, the same single indexed read the token path does, and binds the connection to the owner for its lifetime; link:0001.pinha.git-hosting.adoc[Git hosting] covers what that session may then run. `last_used_at` is written at most once an hour per key, so a fetch loop does not turn into a write per connection, and a rejected key is logged with its fingerprint and the peer address and counted. A connection authenticated before a key was deleted survives until it ends, which is bounded by the fetch or push it is running.

=== Recovery

A user with no usable passkey is recovered by the operator, who authorizes one registration ceremony for that user from the release console, naming the user by email; no message is sent to it, and the same in-memory store holds the claim token. The authorization lives in the node's memory for fifteen minutes and dies with a restart, so nothing persistent can be stolen.

=== Operating

Users persist in Postgres, reached with `DATABASE_URL`. The intended deployment is Neon: TLS with chain verification against the OS trust store, and unnamed prepared statements when the URL names a pooled endpoint, because that endpoint is PgBouncer in transaction mode. Repositories stay on disk and are still backed up by copying the repo root; the database is backed up by Neon. A database outage stops sign-in and token verification, so it stops git transport too.

Widelog lines and trace spans carry the user ID when a request is authenticated, and an SSH session carries the user its key resolved to.

== Data Model

`user_credentials`: `user_id`, `credential_id` (unique), `public_key`, `aaguid`, `sign_count`, `label`, `last_used_at`, inserted timestamp.

`user_sessions`: `user_id`, `token_hash` (unique), `last_used_at`, inserted timestamp.

`user_api_tokens`: `user_id`, `token_hash` (unique), `label`, `expires_at`, `last_used_at`, inserted timestamp.

`user_ssh_keys`: `user_id`, `fingerprint` (unique, SHA-256), `public_key`, `algorithm`, `label`, `last_used_at`, inserted timestamp.

`user_invites`: `token_hash` (unique), `label`, `created_by_user_id`, `expires_at`, `consumed_at`, `consumed_by_user_id`, inserted timestamp.

Every table cascades on user deletion. The `users` table itself is defined in link:0002.pinha.account.adoc[Account].
